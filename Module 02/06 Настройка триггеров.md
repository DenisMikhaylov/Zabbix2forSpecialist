# Лабораторная работа: Настройка кастомных триггеров и макросов в Zabbix 7.4

## Цель работы
Изучить механизм создания пользовательских проверок (`UserParameter`), освоить настройку кастомных триггеров в Zabbix 7.4, а также научиться использовать макросы (встроенные и пользовательские) для параметризации порогов срабатывания и повторного использования логики триггеров.

## Теоретическая справка

**Триггеры** в Zabbix — это логические выражения, которые оценивают данные элементов (items) и генерируют события «Проблема»/«Восстановление». Синтаксис простого выражения: `function(/host/key,parameter)<operator><constant>`. В Zabbix 7.4 поддерживаются функции `last()`, `avg()`, `min()`, `max()`, `change()`, `count()` и другие.

**Макросы** — это переменные, которые подставляются в выражения триггеров, имена элементов, описания и другие поля. Они бывают:
- **Встроенные (built-in)** — например, `{HOST.NAME}`, `{TRIGGER.NAME}`, `{ITEM.LASTVALUE}`, `{DATE}`, `{TIME}`. Используются в основном в оповещениях и описаниях.
- **Пользовательские (user macros)** — имеют синтаксис `{$MACRO}`. Определяются на трёх уровнях:
  - **Глобально:** Administration → Macros;
  - **На уровне шаблона:** в настройках шаблона;
  - **На уровне хоста:** в настройках хоста (переопределяют глобальные и шаблонные значения).
  
  Уровни приоритета: **хост > шаблон > глобальный**. Поддерживаются **контекстные макросы** вида `{$MACRO:context}` (например, `{$DISK_USAGE_MAX:/}`), а также **секретные макросы** (тип *Secret text*) для хранения паролей.

Использование макросов в триггерах позволяет:
1. Задать пороги один раз и переиспользовать их в нескольких триггерах.
2. Изменять пороги для конкретного хоста без редактирования выражений.
3. Делать шаблоны универсальными — один шаблон применяется к разным хостам с разными порогами.

Примеры пользовательских проверок берутся из репозитория [DenisMikhaylov/Zabbix2forSpecialist](https://github.com/DenisMikhaylov/Zabbix2forSpecialist/blob/main/Module%2002/08%20%D0%9F%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C%D1%81%D0%BA%D0%B8%D0%B5%20%D0%BF%D1%80%D0%BE%D0%B2%D0%B5%D1%80%D0%BA%D0%B8.md): мониторинг DHCP (`dhcp.stat`), количество процессов nginx (`ssh.run[nginx_proc]`), процент использования диска (`custom.disk.usage`), число пользовательских сессий (`custom.users`).

## Ход работы

### 1. Подготовка пользовательских проверок (`UserParameter`)

#### 1.1. Мониторинг DHCP (`dhcp.stat`)

Скрипт `dhcp_stat.sh` возвращает значения `MAX` и `CUR` для DHCP-пула. В конфигурации агента:

```ini
UserParameter=dhcp.stat[*],/usr/local/bin/dhcp_stat.sh $1
```

Создаются два элемента данных (тип **Zabbix agent**):
- **Имя:** `DHCP stat CUR`, **Ключ:** `dhcp.stat[CUR]`, тип **Numeric (unsigned)**.
- **Имя:** `DHCP stat MAX`, **Ключ:** `dhcp.stat[MAX]`, тип **Numeric (unsigned)**.

#### 1.2. Количество процессов nginx (`ssh.run[nginx_proc]`)

Элемент типа **SSH agent**, ключ `ssh.run[nginx_proc,,,UTF-8]`, команда `pgrep -c nginx || echo 0`, тип **Numeric (unsigned)**.

#### 1.3. Процент использования диска (`custom.disk.usage`)

```ini
UserParameter=custom.disk.usage,df -h / | awk 'NR==2 {print $5}' | tr -d '%'
```

Элемент данных с ключом `custom.disk.usage`, тип **Numeric (unsigned)**.

#### 1.4. Количество пользовательских сессий (`custom.users`)

```ini
UserParameter=custom.users,who | wc -l
```

Элемент данных с ключом `custom.users`, тип **Numeric (unsigned)**.

После добавления параметров перезапустите агент и проверьте:

```bash
sudo systemctl restart zabbix-agent2
sudo zabbix_agent2 -t custom.disk.usage
sudo zabbix_agent2 -t custom.users
```

### 2. Определение пользовательских макросов

Перед созданием триггеров задайте пороги в виде макросов.

#### 2.1. Глобальные макросы (Administration → Macros)

| Макрос | Значение | Описание |
|--------|----------|----------|
| `{$DISK_USAGE_MAX}` | `85` | Максимальный % использования диска |
| `{$DISK_USAGE_RECOVERY}` | `80` | Порог восстановления по диску |
| `{$USERS_MAX}` | `5` | Максимальное число активных сессий |
| `{$DHCP_USAGE_MAX}` | `90` | Максимальный % использования DHCP-пула |
| `{$CPU_LOAD_CHANGE}` | `2` | Порог резкого изменения нагрузки CPU |

#### 2.2. Макросы на уровне хоста (Host → Macros)

Переопределите значения для конкретного хоста — например, для сервера с большим диском:

| Макрос | Значение |
|--------|----------|
| `{$DISK_USAGE_MAX}` | `95` |
| `{$USERS_MAX}` | `10` |

Это демонстрирует **приоритет макросов**: на этом хосте триггеры будут использовать значения 95 и 10, а не глобальные 85 и 5.

#### 2.3. Контекстные макросы (опционально, для продвинутых)

Если на хосте несколько дисков, можно задать индивидуальные пороги:

| Макрос | Значение |
|--------|----------|
| `{$DISK_USAGE_MAX:/}` | `90` |
| `{$DISK_USAGE_MAX:/var}` | `95` |

В триггере используется `{$DISK_USAGE_MAX:/}` для корневого раздела.

### 3. Создание кастомных триггеров с использованием макросов

Триггеры создаются в **Configuration → Hosts → [ваш хост] → Triggers → Create trigger**.

#### 3.1. Триггер: превышение порога использования диска

**Name:** `Disk usage is too high on {HOST.NAME}`

**Expression:**
```
last(/debian12/custom.disk.usage)>{$DISK_USAGE_MAX}
```

**Recovery expression:**
```
last(/debian12/custom.disk.usage)<{$DISK_USAGE_RECOVERY}
```

**Description:**
```
Disk usage is {ITEM.LASTVALUE1}% on {HOST.NAME} (threshold: {$DISK_USAGE_MAX}%)
```

Здесь используются:
- пользовательские макросы `{$DISK_USAGE_MAX}` и `{$DISK_USAGE_RECOVERY}`;
- встроенные макросы `{HOST.NAME}`, `{ITEM.LASTVALUE1}` в описании.

#### 3.2. Триггер: аномальное количество пользовательских сессий

**Name:** `Too many user sessions on {HOST.NAME}`

**Expression:**
```
last(/debian12/custom.users)>{$USERS_MAX}
```

**Description:**
```
Current sessions: {ITEM.LASTVALUE1}. Threshold: {$USERS_MAX}
```

#### 3.3. Триггер: остановка nginx

**Name:** `Nginx is down on {HOST.NAME}`

**Expression:**
```
last(/debian12/ssh.run[nginx_proc,,,UTF-8])=0
```

**Description:**
```
No nginx processes found. Last check: {TIME} {DATE}
```

Здесь используются встроенные макросы `{TIME}` и `{DATE}`.

#### 3.4. Триггер: приближение DHCP-пула к исчерпанию

**Name:** `DHCP pool usage is high on {HOST.NAME}`

**Expression:**
```
last(/debian12/dhcp.stat[CUR])/last(/debian12/dhcp.stat[MAX])*100>{$DHCP_USAGE_MAX}
```

**Description:**
```
DHCP pool usage: {ITEM.LASTVALUE1}. Threshold: {$DHCP_USAGE_MAX}%
```

Здесь показано использование макроса в вычисляемом выражении с отношением двух элементов.

#### 3.5. Триггер: резкое изменение нагрузки CPU

**Name:** `CPU load changed sharply on {HOST.NAME}`

**Expression:**
```
change(/debian12/system.cpu.load[all,avg1])>{$CPU_LOAD_CHANGE}
```

**Description:**
```
CPU load changed by more than {$CPU_LOAD_CHANGE}. Current: {ITEM.LASTVALUE1}
```

> **Совет:** для каждого триггера задайте **Severity**, **Tags** (например, `scope: resources`, `service: nginx`) и **Operational data** — там также можно использовать макросы (`{HOST.NAME}`, `{ITEM.LASTVALUE}`).

---


#### 4.1. Изменение порога без правки триггера

1. Триггер 3.1 использует `{$DISK_USAGE_MAX}` = 85 (глобально).
2. Измените значение макроса на уровне хоста на **95** (Host → Macros).
3. Убедитесь, что триггер больше не срабатывает при использовании 90% (при условии, что `custom.disk.usage` возвращает такое значение). Это демонстрирует приоритет макросов уровня хоста.
4. Верните значение, чтобы продемонстрировать восстановление.

#### 4.2. Проверка подстановки встроенных макросов

1. Искусственно создайте условие срабатывания (например, снизьте порог `{$USERS_MAX}` до `0`).
2. Дождитесь проблемы в **Monitoring → Problems**.
3. Откройте событие и убедитесь, что в имени и описании подставились `{HOST.NAME}`, `{ITEM.LASTVALUE1}`, `{$USERS_MAX}`.

#### 4.3. Проверка разрешения макросов

В веб-интерфейсе на странице триггера доступна кнопка **Expression constructor**, где можно увидеть итоговое выражение с подставленными значениями макросов (для активного хоста). Убедитесь, что выбранный хост использует именно те значения, которые вы задали (уровень хоста приоритетнее глобального).

---

### 5. Проверка работы триггеров

1. **Искусственное создание условия:** заполните диск, снизьте порог макроса или запустите/остановите nginx.
2. **Monitoring → Problems:** убедитесь, что созданные триггеры появляются при выполнении условий и корректно восстанавливаются после `Recovery expression`.
3. **Тестирование выражений:** в форме создания триггера используйте кнопку **Test** для проверки выражения с реальными значениями.
